# Scoped Workhorse 0.6.1 security disposition

Reviewed October 2, 2026. Target: source-build-only recipe using Workhorse/core/dashboard/server/contract0.6.1, Node24.20.0 pinned by digest, and Debian libpcre2-8-0 `10.42-1+deb12u1`. Final builds must preserve those versions and the original grants/notices; this source review does not attest an unspecified future image.

## Decision and trust boundary

**No concrete default-request-reachable unpatched native trigger was identified among the 31 primary Node-runtime/OS leads reviewed below.** The applied PCRE2 update addresses three of those leads. A separate PostgreSQL-maintainer review identified available application-security fixes missing from 17.9; this recipe therefore also pins PostgreSQL 17.11 as described below. This is a finite, scoped engineering disposition, not a claim that every shipped component is patched, that every path was formally proven unreachable, or that scanner counts establish exploitability. It does not invent a waiver or require zero scanner findings.

The reviewed application runs Node HTTP/1 behind Railway TLS termination, generated Basic authentication for the operator dashboard, bounded JSON task inputs, a private fixed worker implementation, and PostgreSQL through the JavaScript pg driver. It does not accept uploaded executables/archives, arbitrary regex/glob programs, operator shell commands or untrusted worker source as a public feature. App/engine server code reviewed for this target does not launch Perl, mount/nsenter, ACL utilities, infocmp or GNU gzip, load a native .node add-on, call PCRE2, or open outbound WebSocket clients. HTTP readiness alone is not the basis of this assessment.

Node dynamically links glibc/libstdc++/libgcc; those libraries are not dismissed merely because they are OS packages. Each advisory's affected operation is considered separately. Recipe extensions, native add-ons, host privileges, arbitrary archive/glob/URL input, Perl execution or outbound WebSocket clients invalidate the corresponding boundaries and need their own assessment.

The table assesses **31 unique primary native advisory leads**: three are fixed by the pinned PCRE2 update, leaving **28 residual conditions**. Advisory matching is not an exploit count. Scanner severity is distinct from Debian's package status/urgency, architecture prerequisites and application exposure. Debian no-dsa/postponed entries below are context, **not** automatic fixes or waivers.

For the earlier Node upgrade leads, retain the [primary June 2026 bulletin's](https://nodejs.org/en/blog/vulnerability/june-2026-security-releases) severity distinction: upstream CVE-2026-48937 was Medium and CVE-2026-48617 Low, while the scanner/NVD linkage labeled both High. The supported Node24.20.0 pin is not a latest-release claim or blanket clearance of bundled libraries.

## Default Node gzip route versus CVE-2026-85091

The 0.6.1 dashboard server's host.js and static-assets.js import `node:zlib` gzip/brotliCompress. Compression is an actual default feature, including packaged asset gzip at level9 and thresholded RPC responses. It must not be described as absent.

The [primary zlib fix](https://github.com/madler/zlib/commit/df84af25dc1942490e1d1c899a07619152a46148) changes **gzwrite.c**: after a nonblocking write failure it resets avail_in/next_in before later gzip-FILE operations. It is not a general deflate-compressor patch. The [exact Node24.20.0 binding](https://github.com/nodejs/node/blob/v24.20.0/src/node_zlib.cc) initializes GZIP mode through deflateInit2 and operates on z_stream buffers. No gzwrite/gzprintf/gzvprintf/gz_vacate call occurs in that binding. HTTP compressed responses and static asset buffers do not open the nonblocking gzFile writer required by this advisory.

**Result:** no default request-reachable85091 trigger identified for the actual Node gzip emission route. Node's bundled `1.3.2.1-motley-42c2f19` and OS zlib's package/version discrepancy are disclosed, not treated as proof that every zlib consumer is patched. A native add-on or future handler using gzstdio APIs would require a fresh assessment. The primary URLs above identify the exact patch and binding source; no exploit claim or fabricated version clearance is made.

## PostgreSQL application-security patch

The database service pins `postgres:17.11-bookworm@sha256:639ab7ceb90e13123085b741fb31ef493fba25463002f6da665352e7b534b652`. The maintainer release dates are [17.9: February 26, 2026](https://www.postgresql.org/docs/17/release-17-9.html), [17.10: May 14, 2026](https://www.postgresql.org/docs/17/release-17-10.html), and [17.11: August 13, 2026](https://www.postgresql.org/docs/17/release-17-11.html). The 17.11 patch includes the intervening application-security fixes. This is an exact supported patch selection, not a latest-version, complete database-image security or native-library clearance claim.

Private networking limits who can reach PostgreSQL; it does not patch the server. For example, [CVE-2026-6479](https://www.postgresql.org/support/security/CVE-2026-6479/) concerns unauthenticated repeated SSL/GSS negotiation on a reachable Unix socket, or TCP when both mechanisms are disabled. The recipe has no public database endpoint or Kerberos provisioning; every TCP handshake prerequisite was not independently demonstrated. Conversely, the detailed [CVE-2026-14679 advisory](https://www.postgresql.org/support/security/CVE-2026-14679/) requires a database object creator and a crafted function OUT-parameter count; it is not represented here as a generic unauthenticated TCP attack. Available maintainer fixes are adopted without inventing default exploitability for every advisory.

The bootstrap `workhorse` login is a PostgreSQL **superuser** shared by the worker and dashboard. A read-only dashboard feature is not a least-privilege SQL role or an enforced read-only transaction boundary. This scoped recipe supports trusted owner-operated SQL and workloads, not untrusted SQL authors, arbitrary extensions or hostile backup inputs.

Local qualification replaces the gracefully stopped PostgreSQL 17.9 container with 17.11 on the same volume and preserves its cluster identifier and role metadata. It also restores the pre-upgrade dump into an independently empty 17.11 volume while preserving original Workhorse tasks, checkpoints, events, effects and dashboard credentials. No downgrade or cross-major migration is claimed. Server and client-library versions must be distinguished: the selected image reports server package `17.11-1.pgdg12+2` and `libpq5 18.6-1.pgdg12+2`.
